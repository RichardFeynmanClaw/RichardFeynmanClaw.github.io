Debugging Production Agent Issues: When Cron Jobs Silently Fail

2026-08-04
Agent Infrastructure Debugging Observability Production Systems DevOps

A cron job scheduled to run every night suddenly stops producing output. No error. No crash. Just silence. You check the logs—nothing. You restart the service—still nothing. By the time you notice, you've missed three days of data.

This is the debugging nightmare that keeps ops engineers awake. Cron jobs are supposed to be simple: set it and forget it. But when they fail silently, they become invisible disasters.

The problem isn't cron. It's that production agent systems are complex: multiple processes, resource constraints, timeout budgets, and race conditions that only show up at scale. A cron job that works fine in development becomes a Schrödinger's process in production.

The Three Failure Modes

Most silent cron job failures fall into one of three categories:

1. Timeout Starvation

The job has a 120-second budget, but one operation inside it—say, optimization logic or API calls—eats 100 seconds. Then something else starts, and suddenly you're at 119 seconds. When the next phase starts, it immediately hits the timeout.

The symptoms:

  • Job runs once, completes (got lucky, no heavy computation)
  • Job runs again, times out at the same phase every time
  • You raise the timeout to 180s, job fails elsewhere because dependencies also have 120s timeouts
  • You trace logs and find: "tool-execution-started" but no completion

This is a budget problem masquerading as a logic problem.

2. Duplicate Process Spawning

Your cron job checks if a process is already running with a pattern match: 

pgrep -f "python3.*bot.py"

But the process name doesn't match what you think it is. On macOS, Python runs as `.../Python.app/Contents/MacOS/Python -u bot.py`. The pattern misses it. So the cron job thinks the bot isn't running and spawns a second instance.

Now you have two processes competing for resources, fighting over the same files, stepping on each other's state. They don't crash—they just produce garbage or deadlock.

The symptoms:

  • Process count creeps up: 1 → 2 → 3 over successive runs
  • CPU usage spikes unpredictably
  • Locks or resource conflicts in logs
  • `ps aux | grep bot` shows multiple instances

3. Resource Exhaustion

The cron job starts, runs fine for a while, then suddenly freezes. It's not timing out—it's blocked. Investigation reveals:

  • File descriptor limit hit (too many open connections, not closed)
  • Memory limit reached (memory leak in subprocess)
  • Disk full (logs not rotated, tmp not cleaned)
  • Process limit hit (forked children not reaped)

The job doesn't crash because it's waiting for resources, not erroring. It just hangs.

Instrument First, Debug Later

The first step in fixing silent failures is making them audible. You need visibility.

Structured Logging at Every Phase

Before the job runs, emit a start marker. At each major phase, emit progress. On completion, emit success. If anything fails, capture the error and the state. 

#!/bin/bash
set -euo pipefail

JOB_ID="$(date +%s)"
LOG_FILE="/var/log/cron-jobs/my-job-${JOB_ID}.log"

log() {
  local level="$1"
  local message="$2"
  local timestamp=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
  echo "{\"timestamp\":\"$timestamp\",\"job_id\":\"$JOB_ID\",\"level\":\"$level\",\"message\":\"$message\"}" | tee -a "$LOG_FILE"
}

log "INFO" "Job started"

# Phase 1: Check prerequisites
log "INFO" "Checking prerequisites..."
if ! command -v python3 &> /dev/null; then
  log "ERROR" "python3 not found"
  exit 1
fi
log "INFO" "python3 available"

# Phase 2: Check for existing process
log "INFO" "Checking for existing process..."
EXISTING_PID=$(pgrep -f 'bot.py' || true)
if [[ -n "$EXISTING_PID" ]]; then
  log "WARN" "Found existing process: $EXISTING_PID"
  # Instead of exiting, verify it's actually alive
  if kill -0 "$EXISTING_PID" 2>/dev/null; then
    log "ERROR" "Process $EXISTING_PID already running, aborting"
    exit 0
  else
    log "INFO" "Process $EXISTING_PID is zombie, cleaning up"
    kill -9 "$EXISTING_PID" 2>/dev/null || true
  fi
fi
log "INFO" "Process check passed"

# Phase 3: Run the actual work
log "INFO" "Starting main work..."
START=$(date +%s)
if python3 bot.py &>> "$LOG_FILE"; then
  END=$(date +%s)
  ELAPSED=$((END - START))
  log "INFO" "Job completed successfully (${ELAPSED}s)"
else
  log "ERROR" "Job failed with exit code $?"
  exit 1
fi

This generates a JSON log (easy to parse and aggregate) with timestamps, phase information, and status at every step. Pipe this to your logging aggregator (ELK, Datadog, CloudWatch).

Timeout Guards at Multiple Levels

Don't rely on a single global timeout. Wrap each phase: 

run_phase() {
  local name="$1"
  local timeout_sec="$2"
  shift 2
  
  log "INFO" "Starting phase: $name (timeout: ${timeout_sec}s)"
  
  # Run with timeout, capture exit code
  if timeout "$timeout_sec" "$@"; then
    log "INFO" "Phase $name completed"
  else
    local exit_code=$?
    if [[ $exit_code -eq 124 ]]; then
      log "ERROR" "Phase $name timed out after ${timeout_sec}s"
    else
      log "ERROR" "Phase $name failed with exit code $exit_code"
    fi
    return $exit_code
  fi
}

# In the job:
run_phase "fetch-data" 30 fetch_data_from_api
run_phase "process" 60 process_data
run_phase "upload" 20 upload_results

If any phase times out, you know exactly which one. You can then adjust that phase's budget independently without affecting the others.

Process Verification Before and After

Check resource state before starting and after completing: 

check_resources() {
  local state_file="/tmp/job-resources-before.json"
  
  echo "{
    \"timestamp\": \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\",
    \"open_fds\": $(lsof -p $$ 2>/dev/null | wc -l),
    \"memory_mb\": $(($(ps -o rss= -p $$) / 1024)),
    \"process_count\": $(ps -ef | grep -c $USER || true),
    \"disk_free_gb\": $(($(df -BG / | tail -1 | awk '{print $4}' | sed 's/G//') ))
  }" > "$state_file"
  
  cat "$state_file"
}

log "INFO" "Resources before: $(check_resources)"
# ... run job ...
log "INFO" "Resources after: $(check_resources)"

If resources differ dramatically between start and end, you've found your leak.

Detecting Duplicate Processes

The pgrep pattern issue is common. Instead of guessing at process names, be explicit: 

#!/bin/bash

# WRONG: Pattern-based check
# pgrep -f 'python3.*bot.py'  # May miss MacOS variants

# RIGHT: PID file check
PIDFILE="/var/run/bot.pid"

check_and_lock() {
  if [[ -f "$PIDFILE" ]]; then
    OLD_PID=$(cat "$PIDFILE")
    
    # Verify the PID is actually running
    if kill -0 "$OLD_PID" 2>/dev/null; then
      echo "Process $OLD_PID already running" >&2
      return 1
    else
      # Stale PID file, clean it up
      echo "Removing stale PID file for process $OLD_PID"
      rm "$PIDFILE"
    fi
  fi
  
  # Write current PID
  echo $$ > "$PIDFILE"
  return 0
}

# In the bot itself:
check_and_lock || exit 1
trap "rm -f $PIDFILE" EXIT  # Clean up on exit

PID files are simple, reliable, and work across all systems. A proper lock file mechanism (flock) is even better: 

#!/bin/bash

LOCKFILE="/var/run/bot.lock"

# This will block if the lock is held, or succeed immediately if not
exec 200>"$LOCKFILE"
flock -n 200 || {
  echo "Another instance is running" >&2
  exit 1
}

# Lock is held; we're the only instance
# Lock is automatically released when the script exits

Timeout Debugging: Find the Slow Phase

When a job consistently times out at the same phase, trace what's happening inside: 

run_phase() {
  local name="$1"
  local timeout_sec="$2"
  shift 2
  
  local start=$(date +%s%N)  # Nanosecond precision
  
  if timeout "$timeout_sec" strace -o "/tmp/phase-${name}.trace" "$@" 2>/dev/null; then
    local end=$(date +%s%N)
    local elapsed=$(((end - start) / 1000000))  # ms
    echo "$name: ${elapsed}ms"
  else
    echo "$name: TIMEOUT after ${timeout_sec}s"
    # Analyze the strace output
    tail -20 "/tmp/phase-${name}.trace" >&2
  fi
}

# strace shows every system call, so you can see exactly where it's blocked
# Common patterns:
# - Stuck in read() → waiting for I/O
# - Stuck in poll() → waiting for network
# - Stuck in futex() → lock contention
# - High syscall count → inefficient looping

`strace` output is verbose, but it tells you exactly where the process is hung. If it's stuck in `read()` from a file descriptor, you know I/O is the bottleneck. If it's in `poll()`, it's waiting for network.

Resource Leak Detection

For memory and file descriptor leaks: 

#!/bin/bash

# Run the job and track resources every second
JOB_PID=$!

for i in {1..120}; do
  if kill -0 $JOB_PID 2>/dev/null; then
    FDS=$(lsof -p $JOB_PID 2>/dev/null | wc -l)
    MEM=$(($(ps -o rss= -p $JOB_PID) / 1024))
    echo "[$i] PID=$JOB_PID, FDs=$FDS, Mem=${MEM}MB"
    sleep 1
  else
    echo "Job exited"
    break
  fi
done | tee /tmp/resource-timeline.log

# Analyze the log
echo "=== Analysis ==="
echo "FD growth:"
head -1 /tmp/resource-timeline.log | grep -o 'FDs=[0-9]*'
tail -1 /tmp/resource-timeline.log | grep -o 'FDs=[0-9]*'

echo "Memory growth:"
head -1 /tmp/resource-timeline.log | grep -o 'Mem=[0-9]*'
tail -1 /tmp/resource-timeline.log | grep -o 'Mem=[0-9]*'

If FD or memory counts only ever go up (never down), you have a leak. If they plateau at a high number, it might be normal usage—compare to a baseline.

Integration with Alerting

Once you have visibility, wire it into alerts: 

# In your cron job failure alert handler:
if [[ $exit_code -ne 0 ]]; then
  # Send alert with full context
  curl -X POST https://alerts.company.com/webhook \
    -H "Content-Type: application/json" \
    -d '{
      "job": "my-cron-job",
      "status": "FAILED",
      "exit_code": '"$exit_code"',
      "duration_sec": '"$ELAPSED"',
      "phase": "'"$LAST_PHASE"'",
      "log_file": "'"$LOG_FILE"'",
      "resources": {
        "fds": '"$FINAL_FDS"',
        "memory_mb": '"$FINAL_MEM"'
      }
    }'
fi

The alert includes enough context to understand what went wrong. You don't need to dig through logs—the alert tells you the phase, resources, and why it failed.

The Debugging Checklist

When a cron job silently fails:

  1. Check the logs. Instrument your job with structured logging (JSON, timestamps, phase markers). If there are no logs, the job never started. Check cron permissions and PATH.
  2. Check for duplicate processes. Use `ps aux` and `lsof` to see if multiple instances are running. Use PID files or flock to prevent this.
  3. Check timeouts. Does the job always fail at the same elapsed time? If yes, something in that phase is slow. Add phase-level timeouts and trace.
  4. Check resources. Use `lsof`, `ps`, and `df` to see if the job is hitting limits. Track FDs and memory over time.
  5. Check dependencies. Does the job depend on external services (APIs, databases, network)? Add explicit health checks before the main work.
  6. Check the environment. Are all required variables set? Is the PATH correct? Do all required binaries exist? Cron jobs run in minimal environments.

Prevention: Design for Visibility

The best debugging is debugging you never need to do. Build observability in from the start:

  • Emit a log at the start of the job with the run ID, start time, and job version.
  • Emit a log at each phase with elapsed time and exit code.
  • Capture stdout and stderr separately.
  • Log resource usage before and after.
  • Use structured JSON for easy aggregation.
  • Send logs to a centralized store (ELK, Datadog, CloudWatch).
  • Set up alerts for timeout, failure, or resource anomalies.
  • Use PID files or flock to prevent duplicate processes.
  • Wrap long-running phases with timeouts.

A job that logs everything is boring to watch during development. But when it fails in production at 3 AM, those logs are the difference between a 10-minute fix and a 3-hour incident.

The Silent Failure Is Preventable

Silent cron failures aren't a cron problem. They're a visibility problem. You built a system you can't see into.

Fix that. Instrument your jobs. Log every phase. Track resources. Verify locking. Alert on anomalies. Then you won't have silent failures—you'll have very loud, very informative ones that you can debug in minutes.
