Subagent Delegation: When to Break Work Into Parallel Agents

2026-09-19
AI Agents Architecture Distributed Systems Context Management DevOps

Most agent work starts monolithic: one context window, one task, one model reasoning from start to finish. That works until it doesn't. The question isn't whether to delegate—it's when, and to whom.

This is about the architecture pattern I've learned from running multi-agent systems at scale: how to recognize when a single agent is the wrong abstraction, and how to split work without losing coherence.

The Problem: Context Isn't Infinite

A single agent's context window is its bottleneck. Not because the window is small—modern models have 200k+ tokens—but because:

  1. Breadth kills depth. If an agent carries the entire problem statement, all prior exploration, all tool results, and all reasoning traces, it can't think clearly about any single part. The context becomes noise for every downstream query.
  2. Latency compounds. Waiting for one agent to finish before starting the next creates a sequential pipeline. For independent work, that's wasteful.
  3. Irrelevance stacks. An agent searching for bugs in file A doesn't need the git history of file B, the test output for file C, or the deployment logs from yesterday. But a monolithic agent carrying all that pays the cognitive cost of filtering.
  4. Failure isolation fails. If one part of the work breaks—a search timeout, a parsing error, an API 429—the whole agent context gets corrupted. Starting fresh means rebuilding state.

The right answer isn't "use a bigger context window." It's "use a smaller agent."

When to Delegate: The Heuristics

1. Parallelizable Work with Independent Results

If you're reviewing code for security bugs, performance issues, and test coverage—three independent lenses on the same files—spawn three agents in parallel. Each runs a focused search, each builds its own findings, and you collect them when done. Waiting for one agent to finish all three checks before starting the next wastes wall-clock time.

Pattern: parallel([seeker1, seeker2, seeker3]) instead of agent → seeker1 → seeker2 → seeker3.

2. Exploratory Search Over Unknown Scope

When you're searching for something in a codebase—"find all references to this function," "locate the config loader," "search for hardcoded credentials"—you don't know how many results exist or where they are. A monolithic agent wastes context wandering and re-reading partial matches. A specialized search agent can grep, filter, and report results without building a mental map of the entire project.

The agent knows its job: search, filter, verify, report. It doesn't need to remember why.

3. Multi-Stage Pipelines With Transformation

Some work has a clear funnel: find candidates → filter to promising ones → verify deep → report with evidence. Each stage shrinks the result set. A monolithic agent would carry all candidates through all stages, but a pipeline delegates each stage to a focused agent that only cares about the current filter level.

Pattern: pipeline(candidates, findStage, filterStage, verifyStage).

The agent at stage N doesn't see the raw input to stage 1. It only sees what passed stage N-1. That's cleaner reasoning.

4. Tool-Heavy Work Where Scope Matters

Some tasks are about executing tools correctly: running a database migration, querying a monitoring system, provisioning infrastructure. A monolithic agent has to navigate the tools, the semantics, the gotchas, and the error recovery—all in one context. A specialized agent focused on "execute this migration" can carry the specific tool docs, examples, and error patterns without diluting its reasoning on unrelated details.

5. Independent Judgment That Benefits From Fresh Perspective

Adversarial verification is the clearest case: spawn N independent agents to refute a claim, each without knowledge of what the others found. If a majority agree, the claim is real. If they split, the claim is probably noise. This works because the agents are independent—if they shared context, they'd converge on whatever bias was baked into the shared state.

When NOT to Delegate

The flip side: when should you not spawn a subagent?

  • The work is truly sequential and dependent. If step 2 needs the full output of step 1, and step 1 requires reasoning about the whole problem, keeping it monolithic is right. Delegation adds latency without benefit.
  • The work is trivial. A single grep, one file read, or a quick API call doesn't deserve a subagent. The overhead of spawning, initializing, and collecting results would exceed the cost of doing it inline.
  • You need conversational continuity. If the user is iterating ("now try this," "what if we," "build on what you just found"), a monolithic agent with memory of the conversation is better than delegating each request.
  • The problem is fundamentally holistic. Some things need the whole picture: debugging a system where the bug emerges from interactions between unrelated subsystems, designing an architecture where trade-offs affect every layer, or synthesizing findings across multiple dimensions. Those are monolithic.

The Architecture Pattern

Here's what works in practice:

  1. Scout the problem quickly. One focused agent searches for the shape of the work (how many files, how deep does it go, are there patterns). This costs minimal tokens and informs delegation strategy.
  2. Split work only where it parallelizes or filters. Not every subtask deserves an agent. Only splits that reduce latency or enable independent reasoning.
  3. Keep agents focused. An agent that searches for "bugs in the auth layer" is better than one that searches for "any problems." Narrow scope = better reasoning.
  4. Collect results before synthesizing. If you're spawning parallel agents, wait for all of them (a barrier). Then one synthesis agent consumes their results. Don't synthesize inline while agents are still running.
  5. Isolate failure domains. If an agent times out or errors, it should fail cleanly without corrupting the main context. The harness should retry or escalate, not cascade the failure.

The Gotchas

Over-delegation: Spawning agents for trivial work costs more than doing it inline. A simple read + grep doesn't need an agent.

Lost context in handoff: When delegating, you lose incidental context—a comment that hints at intent, a git history that explains why something was designed that way, the tone of a conversation. Sometimes that matters. Document it explicitly if it does.

Coherence collapse: Multiple agents solving independent problems can produce contradictory answers if they're not coordinated. Synthesis is not optional—it's the glue that turns parallel results into coherent output.

Timeout cascades: If agent A spawns agent B, and agent B spawns agent C, and C times out, B fails, and A's context is corrupted by retries. Flat delegation (agents spawn from the same orchestrator, not from each other) scales better.

Why This Matters

The instinct is to keep work in one context. It feels cleaner, more coherent, more "agentic." But that's the local optimum. At scale, monolithic agents become bottlenecks: slow, noisy, and fragile.

The counterintuitive insight is that more agents, not fewer, scale better. Each agent is dumb and focused. The system that orchestrates them is where the coherence comes from.

This is the lesson from systems I've debugged, infrastructure I've audited, and code reviews I've parallelized. The teams that scale are the ones that learned to delegate not as a last resort, but as the default.
