Error Handling in Streaming AI APIs: Why Your Errors Disappear

2026-11-04
Streaming Error Handling API Design Debugging Infrastructure

You proxy a streaming API call. Midway through, the upstream service crashes. You log the error. But the client never sees it—they got their 200 OK response 5 minutes ago, with half the data intact. By the time you discovered the problem, it was already gone, and error handling failed silently.

This is the fundamental problem with streaming. Traditional request-response APIs let you validate, fail fast, and return an error before sending anything to the client. Streaming APIs send headers and data before you know if anything will go wrong. Error recovery becomes a negotiation between partial data and honesty.

The Architecture Problem: Headers Are Final

HTTP response headers go out first, and they're immutable. Once you send a 200 OK with Content-Type: application/octet-stream, you've committed. The client will interpret everything that follows as valid data. There's no HTTP mechanism to say "everything you got so far is wrong; here's an error."

This is why streaming error handling is different from regular error handling. You can't check everything upfront. You have to:

  • Send headers optimistically.
  • Validate and stream data.
  • If validation fails mid-stream, emit an error as part of the data stream.
  • Let the client decide what to do with partial data.

The error becomes protocol-aware. For JSON streaming, it might be a trailing error object. For Server-Sent Events, a special event: error message. For plain text, maybe a prefix or suffix. Whatever the format, the error must be something the client can parse without misinterpreting it as valid payload.

The Real Problem: Errors After the Pipe Closes

Here's the trap. Imagine this setup:

  • Client connects to your proxy.
  • Proxy connects to upstream (Claude, OpenAI, local model).
  • Upstream starts streaming.
  • Proxy pipes data straight to the client.
  • After 30 seconds, upstream crashes or returns a non-200 status.

What happens? The pipe is already open. You already sent data. The client has no reason to check for errors—they're getting what they asked for.

And worse: if the upstream service fails silently—it stops streaming, closes the connection, or returns data without a proper error flag—your proxy might never realize something went wrong. It just sees "connection closed" and finishes the stream cleanly. The client gets incomplete data and assumes success.

A Real Example: The Streaming Proxy Bug

This happened in a Claude API proxy. The proxy is an OpenAI-compatible wrapper around the Claude CLI. Here's the flow:

  1. Client sends OpenAI-formatted request.
  2. Proxy converts it to Claude CLI format.
  3. Proxy spawns a CLI subprocess.
  4. CLI outputs JSON events line-by-line.
  5. Proxy converts each JSON event to OpenAI format and streams it to the client.

The CLI returns structured output including error flags on each line. Something like: 

{"type": "output", "data": "hello", "error": null}
{"type": "output", "data": " world", "error": null}
{"type": "done", "error": null}

If an error occurs: 

{"type": "output", "data": "partial", "error": null}
{"type": "done", "error": "Something went wrong"}

The proxy's streaming handler reads these lines, converts them, and pipes them downstream. But here's the bug: if the CLI returns an error flag in the final done message, the streaming code ignores it. It sends the done message with the error text missing, and the client never knows what happened.

Why? The streaming code assumed "if we got here, everything is fine." It didn't check the error field. It didn't surface CLI failures as part of the stream. It just closed the pipe cleanly.

The Fix: Make Errors Visible in the Stream

The solution is to treat errors as stream events, not as HTTP response codes. Here's the pattern:

  • Always inspect error flags. Even in the final message, even after streaming finishes. If there's an error, emit it.
  • Use protocol-aware error format. For SSE, emit a special event. For JSON Lines, emit an error object. For plain text, prepend an error marker.
  • Include context. Error code, message, timestamp, request ID. Give the client enough information to retry or debug.
  • Flush before closing. Make sure the error is actually sent to the client before closing the connection. Don't lose it in buffering.

For the Claude proxy, the fix looks like: 

// Read the final done message
const doneMsg = JSON.parse(finalLine);

// Check for errors
if (doneMsg.error) {
  // Emit error as an OpenAI-compatible error event
  stream.write(`data: ${JSON.stringify({
    object: "error",
    error: {
      message: doneMsg.error,
      type: "server_error",
      code: doneMsg.error_code || "unknown"
    }
  })}\n\n`);
}

// Close the stream
stream.end();

Now the client sees the error. They can parse it, log it, retry, or degrade gracefully. The error is visible instead of invisible.

Gotchas: Buffering, Timeouts, and Partial Failures

Buffering: If you write an error message to the stream but don't flush before closing, the client might never receive it. The data sits in a buffer and vanishes. Always call flush() or end() to ensure delivery.

Timeouts: If the upstream is slow or hangs, the proxy might timeout and close the connection. The client gets a connection reset instead of a clean error. Set aggressive timeouts on the upstream call, and emit a timeout error as part of the stream before giving up.

Partial failures: The upstream sends 80% of the response, then crashes. You've already streamed 80% to the client. Emitting an error message at the end feels like "by the way, the 80% above might be garbage." It's honest, but not great UX. The alternative: stop mid-stream and emit an error without finishing. This requires a protocol-level error marker (like SSE's event: error) so the client knows to discard partial data.

Invisible failures: Sometimes the upstream closes the connection without returning any error message. Your code sees EOF and assumes success. The only fix: don't assume. Check HTTP status codes, check for error flags in each message, and have a fallback: if streaming completes but there's no explicit "success" marker, treat it as an error.

Design Patterns for Streaming Errors

Different protocols handle this differently. Here are the common patterns:

Server-Sent Events (SSE): Use a special event type. The client listens for both event: message and event: error. Clean separation, simple for the client to handle. 

data: {"content": "hello"}

event: error
data: {"code": "rate_limit", "message": "too many requests"}

:close

JSON Lines: Each line is a complete JSON object. Errors are just another type of object. The client parses each line and checks the type field. 

{"type": "output", "data": "hello"}
{"type": "error", "code": "rate_limit", "message": "too many requests"}

OpenAI-compatible streaming: Uses SSE-ish format with data: {"choices":[...]}. Errors can be signaled with a special data: [DONE] followed by an error object, or with a separate error event. (Note: different clients handle this inconsistently, so test thoroughly.)

gRPC streaming: gRPC has two channels: data and errors. Errors come separately, not interleaved. Much cleaner, but not available over HTTP.

Monitoring: Catch Invisible Errors

Streaming errors are easy to miss because they don't trigger HTTP-level alerts. Set up metrics to catch them:

  • Streaming completion rate: How many streams complete with an error marker vs clean finish? A high error rate means your upstream is unstable.
  • Partial data percentage: When errors do occur, how much data made it to the client before the error? If it's consistently 10%, something systematic is failing.
  • Error-to-close ratio: How many streams close (connection reset) without an explicit error message? These are the invisible failures—they deserve investigation.
  • Time-to-error: How long into the stream does the error occur? Early errors might indicate a validation problem. Late errors might indicate a timeout or upstream crash.

Without these metrics, you'll discover streaming errors only when clients complain about truncated or garbage data.

Why This Matters

Streaming is the future of AI APIs. Real-time responses, lower latency, better UX. But streaming breaks our error-handling intuitions. We're used to "request goes in, response comes back, check for errors." Streaming is "start streaming, hope it works, emit errors inline."

If you're building proxies, SDKs, or infrastructure around streaming APIs, you need to:

  • Always check error flags, even in final messages.
  • Make errors visible as part of the stream, not invisible.
  • Use protocol-aware error formats so clients can parse them.
  • Monitor for partial failures and invisible errors.
  • Test error cases: timeouts, crashes mid-stream, missing error markers.

The alternative is silent failures—and those are the worst kind. A client gets incomplete data, assumes it's correct, and builds on top of garbage. Weeks later, that decision propagates through the system as corrupted output somewhere downstream.

Make your errors loud. Stream them alongside your data. Let clients see failures and handle them properly. That's how you build reliable streaming systems.
