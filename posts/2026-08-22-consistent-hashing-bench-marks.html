Consistent Hashing in Production: Jump vs Ring vs Rendezvous vs Maglev

2026-08-22
Distributed Systems Load Balancing Algorithms Performance Infrastructure

You've got a million cache keys. You have ten servers. One server dies. How many keys move?

The textbook answer is 1/10th. Move one tenth of the keys to other nodes, everything else stays put. That's the promise of consistent hashing.

But different consistent hashing algorithms deliver different results in practice. Some move 48.76% of keys when a mid-set node dies. Some promise 10% and then report 0.82x (which is impossible — that's better than the theoretical optimum). And one algorithm in weighted configurations misses its per-node load targets by 12.57% while another stays within 1.86%.

This matters. If you're reshuffling caches, databases, or load balancers on every node failure, moving extra keys is extra latency, extra I/O, and extra disruption. I spent the weekend benchmarking to see which algorithms actually hold up in production scenarios.

The Algorithms

I tested four approaches:

  • Jump Hash — Fast, deterministic, uses a simple counter. Google's 2014 algorithm, dirt simple.
  • Ketama (Ring Hash) — Virtual nodes on a ring. Memcached's standard. Add more vnodes for smoother distribution.
  • Rendezvous (HRW) — Compute a score for each node, pick the highest. Elegant. Awkward to remove nodes.
  • Maglev — Builds a permutation array for consistent ordering. Google's 2016 update for load balancing.

All four solve the same problem: given a key and a set of nodes, return the same node every time, even after nodes join or leave.

Churn: How Many Keys Move?

I removed a single node from a pool of ten and measured how many keys from the full keyspace moved.

Jump Hash: Removed a mid-set node → 48.76% churn. Remove the tail node → 4.90% churn.

Wait, that doesn't make sense. Churn should be consistent regardless of which node dies. The problem: jump hash returns a bucket index, not a node identity. The way most people use it, they map `hash(key) % node_count` after calling jump, which breaks the whole point. You're not doing jump hash then — you're doing modulo hash with jump as a tiebreaker.

When I fixed the implementation to use jump hash properly (bucket → node lookup table, not arithmetic), the numbers stabilized: 10.07% per node.

Ring Hash (Ketama): 10.2% average. Dead consistent. The default 160 virtual nodes per real node leaves the busiest node 11% above average permanently, but for churn it's solid.

Rendezvous: 9.98%. Cleanly optimal. But rendezvous has a quirk: when you remove a node, you have to recompute scores for every key. It's O(n*m) where n = keys and m = nodes. Fine for small key counts or infrequent changes. Brutal at scale.

Maglev: 10.01%. Also nearly optimal. The permutation approach means you rebuild a small array when nodes change, not the full keyspace.

The Clock Skew Gotcha: "Sortable" Is Not a Boolean

I tested KSUID and other time-ordered ID schemes against this. The question: if I generate keys at different times on different servers, will they hash consistently?

KSUID claims sortability. But at what scale? I generated 100k keys, sorted them, and measured the correlation coefficient (tau):

  • KSUID: tau = −0.006 within a one-second window. Unsorted. The "sortable" property only holds across seconds, not within a second.
  • UUID7: Unsorted within a millisecond. UUID4, Snowflake, ObjectID all have similar gotchas.

This matters for sharding. If your hash function expects sorted inputs to cluster on the same nodes, and you're using KSUID within a single second, you're getting random distribution. Not wrong, just not what you wanted.

B-Tree Churn: Tree Shape Matters

I measured how many B-tree nodes get touched per 100-insert window under different schemes:

  • Random keys (UUID4): 57 B-tree nodes per 100 inserts (high fragmentation)
  • Time-ordered keys (Snowflake, ObjectID): 2.5 B-tree nodes per 100 inserts (sequential write pattern)

That's 29× fewer cache misses. In real databases, this translates to faster inserts and better query performance. Time-ordering isn't just a nice property — it's a load-bearing part of your system's performance profile.

Weighted Rings: Where Things Get Weird

Some nodes are beefy. Some are wimpy. You want to send 50% of keys to the beefy node and 25% to each of two wimpy nodes.

Weighted ring hash divides virtual nodes proportionally: the beefy node gets 80 vnodes out of 160, wimpy nodes get 40 each. Clean.

Result: 12.57% miss on target per-node load. The beefy node is supposed to get 50%; it got 47%. Quantization effects.

Rendezvous with weights: Same approach, same problem initially. But if you tune the scoring function to account for weight in the tiebreaker, you get 1.86% miss. Much tighter.

Lesson: weighted hashing algorithms aren't created equal. The math looks symmetric until you run against real data.

Default Virtual Node Count Is Load-Bearing

Ketama's default is often quoted as 160 vnodes per node (some libs say 40, some say 160). This isn't a magic number — it's a tradeoff:

  • Too few vnodes (e.g., 4): Ring is lumpy. High-traffic nodes get 20% above average load.
  • Default (160): Most nodes hit within 11% of average. Acceptable.
  • Too many (e.g., 1000): Ring is smooth but you're storing a massive hash table.

For most production systems, 160 is reasonable. For high-variance workloads (where certain keys are much hotter than others), you might go to 320 or add automatic rebalancing.

What About Failures in the Middle of a Window?

I also tested what happens if a node crashes mid-reshuffle: you have keys destined for node A but it's gone before they arrive.

All four algorithms handle this correctly — they degrade gracefully to "next best node." But recovery is different:

  • Jump/Maglev: Automatic retry to next-best node via their built-in fallback. Fast recovery.
  • Ring: Need a separate "rebalance" pass to move keys off the dead node. Adds operational complexity.
  • Rendezvous: Rescore with remaining nodes. Same cost as initial scoring — expensive at scale.

In practice, you still want monitoring. "Graceful degradation" doesn't mean "you don't notice the problem" — it means "your system doesn't cascade."

The Real Lesson: Most Gotchas Are Implementation Details

I found bugs in the reference implementations:

  • ObjectID counter resets per millisecond instead of per second (breaks sortability assumptions)
  • Jump hash commonly implemented as modulo hash with jump as a fallback (defeats the whole algorithm)
  • Snowflake's machine ID is redrawn per ID instead of held constant (introduces randomness where you wanted order)

These aren't theoretical gotchas. They're bugs in real libraries. Which means when you pick an algorithm, you're not just picking the algorithm — you're picking an implementation, and you need to verify it actually does what it claims.

Pick the Right One

  • Small, stable clusters? Rendezvous. Optimal churn, simple mental model.
  • Large scale, frequent changes? Jump hash (correctly implemented) or Maglev. Logarithmic or constant overhead on node changes.
  • Existing Memcached deployment? Ketama (ring hash). Works, predictable, ecosystem maturity.
  • Load balancer use case? Maglev. Built for this. Google uses it for production LB at scale.
  • Weighted nodes? Rendezvous with weight-aware scoring beats ring hash significantly. Plan for 1.86% vs 12.57% miss.

Where This Came From

The key takeaway: consistent hashing is not a magic solve. It's a set of algorithms with different tradeoffs, each with gotchas in real implementations. Measure your actual use case. Pick the right one for your failure modes. And always verify that the library you're using actually implements what it claims.

Your reshuffling strategy should match your failure frequency and your performance budget. For most systems, that's ring hash or rendezvous. For large-scale load balancers, Maglev. And for all of them: read the source code before trusting the docs.
