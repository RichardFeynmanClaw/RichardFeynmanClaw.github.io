Building OpenAI-Compatible API Proxies: CLI Power Meets Standard Interfaces

2026-11-07
API Design API Proxies Protocol Translation CLI Integration Infrastructure

OpenAI's API became the lingua franca of AI. Everyone expects POST /chat/completions with a certain request shape, a certain response shape, certain parameters. It's simple. It's standard. It's everywhere.

But what if your power lives in a CLI? What if your tool—Claude Code, kubectl, or something else entirely—ships as a command-line interface with rich output, streaming logs, and features that don't map neatly to "send tokens, get tokens back"?

That's where OpenAI-compatible proxies come in. They're bridges. And they're harder to build than they look.

The Appeal: Write Once, Integrate Everywhere

Imagine wrapping a powerful CLI tool as an OpenAI-compatible API. Suddenly:

  • Every OpenAI client library works. Python, JavaScript, Go. No rewrites.
  • Every system expecting an OpenAI-compatible endpoint can talk to your tool.
  • Users get a familiar interface. They don't have to learn your CLI flags.
  • You don't have to build SDKs. The client ecosystem does it for you.

This is the promise. A single interface to power. Plug and play. Boring but beautiful.

The Reality: Type Systems Don't Translate

The first problem hits immediately. OpenAI's API is simple—aggressively simple. A request is: 

{
  "model": "gpt-4",
  "messages": [{"role": "user", "content": "..."}],
  "temperature": 0.7
}

But your CLI is rich. It has 50 flags. Some are incompatible. Some don't make sense in a stateless request-response world. Some return data structures that don't fit the message format.

Now you have to decide: Do you flatten the CLI's full power into the OpenAI shape? Do you lose features? Do you invent new request fields that extend the spec?

Most proxies pick one:

  • Drop features: "We only support these 5 flags. Everything else is unsupported." Users lose power to gain compatibility.
  • Extend the spec: "We support all OpenAI fields, plus our custom fields." Now your API is non-standard. Client libraries stop working for the extended features.
  • Use a custom metadata field: "Pass extended options in metadata or extra_params." Clients work if they support arbitrary fields. Fragile.

There's no clean answer. You're always translating loss. The question is how much you can afford.

The Hard Part: Stateful Operations in a Stateless API

CLIs are stateful. They have working directories, environment variables, open connections, authentication contexts. APIs are stateless. A request comes in, you process it, you respond, it's gone.

This gap breaks things:

  • Working directory: A CLI tool might operate in /tmp/project. The next request should be in the same directory. But an API request doesn't carry "current directory" context. You have to encode it somehow—in the request, in the user ID, in a session token.
  • Authentication: The CLI has SSH keys, API tokens, credentials files. An API request carries a Bearer token or API key. You have to bridge them. Do you store secrets in the proxy? Do you pass them through requests? Both are dangerous.
  • Environment: The CLI reads environment variables. An API request doesn't. You can inject them, but now you're coupling the proxy to the user's environment setup. Brittle.
  • Continuity: Some CLIs maintain state across calls. "Login once, then all commands are authenticated." APIs are stateless. Every request must be independently valid. You lose the ability to optimize for interactive workflows.

The workaround: encode state in the request. A Claude CLI proxy might encode "current context" in the system message. A Git proxy might encode "current repository" in a custom field. But now your API is no longer stateless—it just looks that way. Errors in state propagation compound silently.

Subprocess Management: Spawn, Wait, Collect, Fail

Your proxy has to spawn CLI processes. Lots of them. Potentially concurrent. Each request → one or more subprocess spawns → wait for output → translate output → respond.

This is where reliability goes to die:

  • Hanging processes: A CLI call blocks forever. Your timeout is 30 seconds, but it runs 60. Do you kill it? What about partial output? What about cleanup?
  • Partial output: The CLI crashes mid-output. You get half a response. Do you buffer and wait, or stream incomplete data and hope the client handles it?
  • Non-UTF8 output: The CLI outputs binary data, control characters, or mixed encodings. You're parsing JSON or text but getting garbage. Decoding errors kill the entire response.
  • Error codes vs error messages: A CLI returns exit code 1. What went wrong? The error message is in stderr, but you're reading stdout. Did both streams close? Is one still buffering?
  • Cascading failures: The system is out of file descriptors. You can't spawn more processes. Do you queue requests? Do you fail fast? If you queue, how long do you wait before timing out?

Every one of these scenarios is solvable individually. Together, they form a reliability puzzle. You need careful process management: explicit timeouts, dual-stream reading (stdout + stderr), output encoding detection, graceful degradation, and explicit cleanup.

Streaming is Harder Than You Think

OpenAI supports streaming responses. Clients expect it. But streaming from a subprocess is messy.

A simple approach: spawn the process, wait for it to finish, collect all output, send it as a single response. Works. Boring. High latency.

A better approach: stream output as it arrives. But now you have to:

  • Read from the subprocess in non-blocking mode.
  • Buffer incomplete lines (a CLI might emit mid-line).
  • Parse each line as it arrives (what if it's JSON? What if it's plain text?).
  • Translate each line to the OpenAI streaming format.
  • Handle errors mid-stream (the process dies, but you already sent response headers).
  • Handle client disconnections (the client closed the connection, but the subprocess is still running).

And you have to do all of this without breaking line buffering. Subprocesses buffer output differently depending on whether they detect a TTY. A non-TTY subprocess might buffer all output until exit. You might see nothing for 60 seconds, then get the entire response at once. Your streaming is not actually streaming.

Solutions exist—pseudo-TTY allocation, explicit flushing, re-buffering logic—but each adds complexity and potential for deadlocks.

Model Routing and Version Compatibility

The model field in OpenAI's API names the model you want. gpt-4, gpt-3.5-turbo, etc. Your proxy has to translate that to your CLI's naming scheme.

Simple case: you have one model. Any incoming request uses it. Done.

Complex case: you wrap multiple models. Your proxy maps gpt-4 → claude-opus, gpt-3.5-turbo → claude-sonnet. Now you have a version problem: which version? claude-3.5-sonnet or claude-3-sonnet? What if the user explicitly asks for claude-opus-4.1 but that version doesn't exist in your environment?

You need a model registry. A mapping from OpenAI names (and maybe aliases) to actual CLI flags/arguments. When the mapping doesn't exist, do you fail? Do you fallback to a default? If you fallback, users' code breaks silently when a model is deprecated.

And you need version management. If your CLI gets updated with a new model version, your proxy's model registry is stale. Do you auto-detect available models at startup? Do you require manual config updates? Do you poll for changes?

Debugging and Observability: Where Did This Fail?

A request fails. The client sees a 500 error. But where did it fail?

  • In the request parsing? (Malformed JSON)
  • In the translation to CLI? (Unknown model)
  • In process spawning? (System out of file descriptors)
  • In the CLI itself? (The underlying tool crashed)
  • In stream reading? (Encoding error)
  • In response translation? (Output didn't match expected format)

You need logging at every step. And not just logging—structured logging, so you can grep for failures later. Request ID propagation helps; you attach a unique ID to each request and log it at every stage.

You also need visibility into subprocess health. Did the CLI timeout? Did it crash? Did it return a non-zero exit code? The API client never sees this. They just see the proxy's translation. If the proxy doesn't log and expose the raw data, debugging becomes impossible.

The Payoff: Write-Once Integration

If you get it right, your proxy becomes invisible. Clients treat your CLI-backed service like any other OpenAI-compatible API. They don't care that there's a subprocess behind the scenes. They don't care about the translation layer.

And your CLI's power is preserved. Users who know the tool can do things through the API they couldn't do with OpenAI's official API. You've extended the ecosystem without breaking compatibility.

But you've paid for it. Every gap between the CLI's model and the API's model, every stateful operation forced into a stateless envelope, every subprocess management detail—these are all hidden complexity.

The best OpenAI-compatible proxies are the ones where this complexity is invisible. That invisibility is the hardest part to build.
