Streaming Protocol Translation for AI: The Invisible Hard Part

2026-10-31
API Design Streaming Protocol Translation AI Integration Infrastructure

Building an API proxy that wraps one model behind another's interface looks simple on the surface: accept request A, call model B, return response C. But real-time streaming breaks every comfortable assumption. Buffering kills latency. Format mismatches corrupt output. Type systems don't cross network boundaries cleanly. This is where proxy architecture earns its complexity.

Why Buffering Is Not An Option

The naive approach: buffer the entire response, transform it, send it back. Clean, simple, wrong.

A 10,000-token response at 100 tokens/second takes 100 seconds. If you buffer it all before sending, your client stares at a blank screen for 100 seconds, then gets flooded with text. Networks timeout. Browsers disconnect. Users think the API is broken.

Real-time streaming means streaming *through* the proxy. The moment the upstream model emits a token, your proxy unpacks it, repacks it, and sends it downstream. Latency adds up (microseconds per transformation), but it's sub-second, not 100-second buffering.

This changes everything about how you structure the code. Your request handler can't wait for a complete response. It has to be a streaming pipeline: read token from upstream, transform, write token downstream, repeat.

Format Translation Without Tearing

Claude's streaming format (Server-Sent Events) and OpenAI's (also SSE, but different field shapes) *look* compatible until they don't.

Claude sends: 

event: content_block_delta
data: {"type":"content_block_delta","delta":{"type":"text_delta","text":"Hello"}}

OpenAI expects: 

data: {"object":"text_completion","choices":[{"delta":{"content":"Hello"}}]}

Both are JSON. Both are streaming. Neither format is compatible with the other without translation.

The hard part isn't writing one transformation—it's maintaining streaming semantics through it. OpenAI clients expect specific events in specific orders. Claude's stream has different event types. A missed reordering or a dropped field will cause client libraries to hang, crash, or produce corrupted output.

The solution: validate both formats as you translate. Parse *every* event from upstream. Verify every required field exists. Emit downstream events in the order the client expects. If a transformation can't be done cleanly, fail loudly and early, not silently at the client.

Type Safety Across The Boundary

TypeScript catches mistakes at compile time—until you cross a network boundary. Then JSON is just strings.

A proxy sits at the boundary. It parses untrusted input (upstream responses) and emits output to clients. Both sides can have schema changes. A model API that adds a new field you don't know about. A client library that starts requiring a field you've never seen. A breaking change in the streaming format between API versions.

Type guards matter here. Not just TypeScript interfaces (those are compile-time only). Runtime validation: check that parsed JSON matches the expected shape. Narrow types explicitly. Catch format violations before they propagate. 

// This catches upstream schema changes at parse time
const parseClaudeEvent = (data: unknown): ClaudeStreamEvent => {
  const parsed = JSON.parse(data);
  if (parsed.type === 'content_block_delta' && parsed.delta?.type === 'text_delta') {
    return { type: 'text_delta', text: parsed.delta.text };
  }
  throw new Error(`Unknown event shape: ${JSON.stringify(parsed)}`);
};

This way, unknown formats fail visibly at the proxy, not at the client.

Error Handling At Two Scales

Errors in a streaming context are tricky. Some errors happen before streaming starts (authentication, rate limits). Some happen mid-stream (model timeout, network glitch). The client experiences them differently.

Pre-stream errors: close the connection cleanly, send an error response in the expected format. The client gets a complete, valid response that says "this request failed."

Mid-stream errors: you've already sent headers and started the body. You can't send a normal error response—it would corrupt the stream. You have to emit an error event *in* the stream format itself. OpenAI clients know to look for `error` events. If you don't send one, the client gets partial output and doesn't know it failed.

Both require different code paths. Both need tests. One missing error handler makes the proxy silently drop requests.

Practical: The Adapter Pattern

Good proxy code separates three layers:

  • Input adapter: Parse client requests, validate against the client's API schema, convert to an internal canonical format.
  • Core logic: Call the upstream model with the canonical request, get back a canonical response stream.
  • Output adapter: Convert the canonical stream back to the client's expected format, emit it.

This keeps format translation localized. The core logic doesn't know or care that OpenAI calls it "content" and Claude calls it "text". Adapters handle that. If a new model needs wrapping, you add input and output adapters—the core stays the same.

Type guards belong in each adapter. The canonical format is strictly defined. Transformations fail loudly if the input doesn't match.

Why This Matters

A proxy isn't just a forwarding layer. It's where you enforce API contracts, handle failure modes that neither upstream nor downstream handles alone, and maintain streaming semantics across format translations.

Get streaming wrong, and you've added latency and complexity without gaining any of the benefits of real-time updates. Get format translation wrong, and you silently corrupt data. Get type safety wrong, and you catch errors at the client, not at the proxy where you can log them and retry.

The invisible part of proxy architecture is doing all three correctly, all the time, under load, with different models and clients evolving independently.

That's where the real work is.
