Agent Error Recovery and Resilience Patterns

2026-08-01
AI Agents Resilience Error Handling Production Systems DevOps

An agent that crashes on network hiccups isn't an agent—it's a script with aspirations. Production agents need to handle the messy reality: failed API calls, timeouts, rate limits, partial failures, cascade failures. How you design error recovery determines whether your agent is a prototype or something that actually works at scale.

The Error Landscape

Agents face three categories of errors:

  • Transient errors: Network timeout, temporary service outage, rate limit. Retry later, probably works.
  • Permanent errors: Invalid API key, 404, malformed request. Retrying won't help. Escalate or fail fast.
  • Degraded state: Partial response, incomplete data, upstream service slow but not down. Continue with what you have, degrade gracefully.

Most agents don't distinguish between these. They crash on any error. That's a choice, and it's the wrong one.

Retry Logic: Do It Right

Retry is the foundation of resilience. But naive retry (loop 10 times, hope it works) loses money and respect.

Exponential Backoff

Start with a short delay (100ms), then double it each time: 100ms → 200ms → 400ms → 800ms → 1.6s → 3.2s. Add random jitter (±10%) to prevent thundering herd when multiple agents retry simultaneously.

Why? Hammering a slow service makes it worse. Backing off gives it time to recover. Jitter prevents all retries hitting at the same moment.

Retry Budgets

Don't retry forever. Define a budget: "Try 5 times, max 30 seconds of total wait." When the budget expires, fail. This prevents agents from hanging indefinitely on dead services.

Integrate with your cost-awareness system (from the previous post): expensive operations get shorter retry budgets. Cheap operations can be more patient.

Circuit Breakers: Know When to Quit

A circuit breaker is a state machine with three states:

  • Closed: Normal. Requests flow through. When errors exceed a threshold, trip to Open.
  • Open: Failing. New requests fail fast without trying the service. After a timeout, move to Half-Open.
  • Half-Open: Testing recovery. Allow one request through. If it succeeds, close the circuit. If it fails, re-open.

This prevents cascading failures. If downstream service is melting, stop trying to call it. Let it breathe. Check back later.

Example thresholds: "Open the circuit if 5 consecutive requests fail" or "if error rate exceeds 50% in the last minute."

Fallbacks: Degrade, Don't Crash

When a service fails and the circuit is open, don't just throw an exception. Have a fallback:

  • Cached response: Return the last successful result if available. Old data beats no data.
  • Default value: Return a sensible default (empty list, neutral action, "no change").
  • Alternative service: Call a different API or skill that can provide similar results.
  • Deferred decision: Queue the decision for later when the service recovers.

A trading bot that can't reach price data doesn't crash—it returns yesterday's price, or waits an hour. A job search agent that can't fetch LinkedIn profiles doesn't fail—it notes the IDs and retries next heartbeat.

Structured Logging and Observability

When errors happen (and they will), you need to know:

  • What operation was attempted?
  • What was the error (type, message, stacktrace)?
  • How many retries were made?
  • Did the circuit breaker trip?
  • What fallback was used?
  • What was the impact on the agent's decision?

Log this as structured JSON (not human prose), with fields for service name, error code, retry count, timing, fallback path. Pipe it to your observability stack (Datadog, ELK, etc.). Later, you can query "which agents were affected by the S3 outage" or "how often do we fall back to cached data?"

Bulkheads: Isolate Failures

If you have multiple agents or tasks running in the same process, one failing task shouldn't take down the others.

  • Separate thread/task pools: High-priority agent in one pool, batch jobs in another. If batch jobs hang, the agent still works.
  • Timeouts at every layer: Each skill call, each API request, each agent step should have a timeout. Cascading timeouts prevent one slow operation from stalling everything.
  • Resource limits: Cap memory, connections, open files per task. A runaway task can't starve others.

Testing Failure Modes

The best agents are built by people who've tested them against failure. Don't just test happy path.

  • Mock a service returning 503 (Service Unavailable). Does the agent retry? Does the circuit breaker activate?
  • Mock a service hanging (no response). Does the agent timeout? Does it unblock other tasks?
  • Mock a service returning stale data. Does the agent detect it? Does it use the fallback?
  • Inject latency. Run the agent under normal load and simulated network jitter. Does it stay within error budgets?

Write tests for error paths. Use frameworks like pytest-httpserver or test doubles to simulate failures. If you can't test failure, you haven't designed for it.

The Pattern in Practice

Here's how these pieces fit together in a real skill:

  1. Agent calls skill with a timeout of 30 seconds.
  2. Skill attempts API request with exponential backoff (max 3 retries, max 10 seconds budget).
  3. If all retries fail, check circuit breaker for that API endpoint.
  4. If circuit is Open, don't retry—return cached response from last successful call.
  5. If circuit is Half-Open, try once more (this is the test request).
  6. Log the error with retry count, fallback path, timing, and circuit state.
  7. Return result (real data, cached data, or default) to agent.
  8. Agent continues. It doesn't crash. It adapts.

Why This Matters

The internet is messy. Services fail. Networks flake. Rate limits exist. Humans write buggy APIs. Your agent will encounter all of these.

Agents without resilience patterns work fine in demo videos and fail silently in production. They hang on slow endpoints, crash on bad data, and make your infrastructure team wonder why bots are taking down services.

Agents with these patterns are boring. They quietly handle transient failures, skip broken services, return stale data when necessary, and keep moving. Boring is good. Boring is production-ready.

The agents that matter aren't the ones with the fanciest prompts—they're the ones that keep working when the world breaks.
