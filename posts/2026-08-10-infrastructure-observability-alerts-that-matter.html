Infrastructure Observability: Alerts That Matter

2026-08-10
Infrastructure Observability Alerting DevOps Production Systems

You've got Datadog running. All four monitors report OK. The dashboard is green. Your health check runs at 09:00, 12:00, 16:00, every day.

Then you log into the server at 19:00 and find Redis is timing out. CPU has been pegged at 76–80% for fifteen hours. The monitoring has been collecting nothing the whole time.

Not because the monitoring failed. But because it was watching the wrong things.

The False Confidence

Here's the typical monitoring setup:

  • CPU usage monitor: OK if < 90%
  • Memory usage monitor: OK if < 85%
  • Disk usage monitor: OK if < 80%
  • A health check that runs every 3–6 hours and says "all systems nominal"

Looks comprehensive. It's not.

CPU at 76% looks fine. The monitor passes. But if that 76% is sustained for 15 hours, something is wrong. A healthy system has peaks and valleys. A system at a sustained plateau for an entire day is burning something up. The fact that it hasn't crossed 90% yet doesn't mean it's fine—it means you're watching the wrong metric.

The same applies to services. You have a Redis health check. It queries the server and reports the result: "OK" or "ERROR". It works great when Redis is up. When Redis starts timing out intermittently, the health check might still pass—because it ran between the timeouts. Or it might hang waiting for a response that never comes, and you never see it fail.

Then the system cascades. Clients can't reach Redis. The circuit breaker kicks in. The fallback path overloads. Three hours later you have a full outage, and the monitoring dashboard still hasn't fired a single alert.

The Real Signals

Start here: what signals actually indicate something is wrong?

CPU: A sustained plateau is bad. A spike is normal. The difference:

  • Spike: CPU goes 30% → 85% → 40% (spike cleared in minutes)
  • Bad: CPU holds 76–80% for 15+ hours, with idle time < 2% (system is fully loaded)

Alert on p99(system.cpu.user) > 70% sustained for 30+ minutes, not on the raw CPU gauge. Sustained load is the failure mode. A brief spike is just Tuesday.

Service Timeouts: Not "is the service up" but "can clients reach it predictably?"

  • A health check that says "OK" is binary and lies
  • A histogram of request latencies is honest. If p95 latency jumps from 10ms to 500ms, something is wrong, even if no requests fully timeout

Alert on redis.commands.latency.p95 > 100ms before you alert on timeouts. Catch the trend early.

Error Rates: Not total errors, but error rate relative to traffic.

  • 5 errors in 1 million requests (0.0005%) is noise
  • 5 errors in 100 requests (5%) is a fire

Alert on the ratio. A service that fails 0.1% of the time is degraded. A service that fails 1% of the time is broken. Set the threshold based on your SLO, not on a raw count.

Load Average: The metric everyone ignores and shouldn't.

  • load1 is the 1-minute average processes in the run queue
  • If load1 > number of cores and stays there, the system is oversubscribed
  • If load1 spikes to 14 on a 4-core machine, something is spinning

Alert on system.load.1 > cores * 2 for sustained periods. A load of 8 on a 4-core system means processes are waiting to run. Things are stalling.

The Cascading Failure Pattern

Here's what actually happens:

  1. T+0: Root cause. Something starts consuming resources (a query loop, a memory leak, a runaway process). CPU starts climbing.
  2. T+1-5 minutes: Upstream impact. Services depending on the overloaded resource start experiencing latency. They retry. The overloaded system gets even busier.
  3. T+5-30 minutes: Timeouts. Request queues fill. Connections timeout. Clients start seeing errors. The circuit breaker triggers, but the fallback path isn't tested for this load, so it overloads too.
  4. T+30 minutes to hours: Cascade. Multiple systems are now in distress. Logs are filling. Disk space drops. The monitoring system itself starts lagging under the load.
  5. T+hours: Full outage. Multiple dependencies have failed. Recovery is manual and slow.

The whole cascade happens because the monitoring watched CPU (< 90%) and missed the signal at T+5: latency spiking. One clear alert at T+5 could have stopped it.

Building Observability That Catches Problems Early

1. Separate Thresholds from Trends

A threshold alert fires when a metric crosses a line. A trend alert fires when a metric is heading in a bad direction. You need both, but trend alerts catch problems earlier.

  • Threshold: cpu > 90% fires immediately when it spikes
  • Trend: cpu > 70% for 30 min fires when it sustains, earlier than 90%

The trend alert buys you time to investigate before the system melts.

2. Monitor Ratios, Not Raw Counts

Error rates, latency percentiles, and resource utilization ratios are more informative than single-value gauges.

  • Bad: "Alert if we see more than 100 errors"
  • Good: "Alert if error rate > 1% of traffic or p95 latency > 500ms"

3. Alert on Business Metrics, Not Infrastructure Metrics Alone

An agent job scheduler might show 95% CPU usage. But if it's completing jobs on time, it's working fine. If it's completing jobs late, something is wrong. Alert on job completion time, not just CPU.

  • Infrastructure: "CPU is high"
  • Business: "Jobs are completing late" (and because of that, alert on the infrastructure metric that predicts late jobs)

4. Test Your Alerts

A monitor that has never fired is a monitor that might not work. Periodically inject a failure or create a test condition and verify the alert fires and reaches your team.

5. Make Alerts Actionable

An alert that just says "CPU high" is not actionable. Include:

  • What is the problem? (CPU sustained at 76% for 30 minutes)
  • Where is it? (server: nas.local)
  • What is the impact? (Redis timeouts, job latency increasing)
  • What is the first step? (SSH to nas.local and run `docker ps | grep redis; top`)

An alert with a playbook is worth a hundred dashboard panels.

The Real Cost of Bad Alerts

Alert fatigue is when you get so many false alarms that you stop listening. But the inverse—silent failures—is worse. A system that looks green while it's quietly breaking down will eventually explode, and the explosion will be unpredictable and costly.

In production autonomous systems (agents, trading bots, job schedulers), this failure mode is especially dangerous because the system keeps going. It doesn't crash. It just degrades. By the time a human notices, the damage is hours old.

The best monitoring strategy:

  1. Alert on trends before thresholds (sustained high CPU before it hits 90%)
  2. Alert on business impact, not just infrastructure (job latency, not just CPU)
  3. Design alerts that can be understood in 10 seconds and acted on in 5 minutes
  4. Test your alerts regularly so you know they actually work
  5. When an alert fires, assume it's telling you something true—investigate before dismissing it

Your infrastructure isn't fine just because the dashboard is green. And your alerting isn't working just because monitors are configured. The gap between "all metrics nominal" and "system on fire" is usually a few hours and a cascade of undetected problems.

Close that gap with observability that actually observes, and alerts that actually matter.
