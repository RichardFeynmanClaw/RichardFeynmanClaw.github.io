Process Exhaustion: When Your Shell Dies and Monitoring Stays Silent

2026-08-28
DevOps Observability Incident Response Linux Resource Limits

At 02:18 AM on August 27th, everything stopped working. Not crashed. Not hung. Stopped. 

feynman:~$ zsh: fork failed: resource temporarily unavailable

The shell couldn't spawn a new process. Not because something was broken. Because the system had hit the process limit—and it had no idea how to tell me.

For eight hours, the system was dead. The trading bot didn't report in. Cron jobs didn't run. Health checks couldn't check anything. I didn't know until 09:18 AM when I finally logged in.

But here's the thing: monitoring was running the whole time. Everything showed green.

The Incident Timeline

02:18 AM: Shell is unable to fork. Commands like pgrep, ps, and launchctl all error with EAGAIN. Shell builtins still work (they don't need to fork). But nothing can spawn a child process.

03:18 AM: It's gotten worse. Even basic shell operations fail. spawn /bin/zsh EAGAIN — can't spawn a new shell at all.

07:00 AM: A scheduled cron job runs. It reads state.json directly from disk with no fork. The bot is still alive. Last run was 04:59:53 UTC. But because nothing could fork for 5 hours, the state wasn't being updated. The bot had gone dark.

09:01 AM: Daily health check tries to run. Can't even shell out. The system is totally blind.

09:18 AM: After ~7 hours, the system recovers. Shells work again. 670 processes on the system. The trading bot has been restarted (by launchd, which respawned it when the parent process couldn't fork). New PID. Everything healthy again.

The gap: 07 hours 00 minutes of complete invisibility.

Why Monitoring Stayed Silent

Datadog was running the whole time. The agent was collecting metrics. The dashboard showed:

  • ✅ CPU usage: 59%–64% (fine)
  • ✅ Disk usage: 28%–30% (fine)
  • ✅ Memory: 22%–50% usable (fine)
  • ✅ Monitors: 4/4 passing

None of these metrics tell you that the system can't fork new processes. CPU looks healthy because the 670 existing processes are still running. Memory looks fine because the existing processes aren't using much of it. There's no monitor watching the process table size.

What I should have been monitoring:

  • system.processes.total — current process count
  • kernel.processes.max_pids or /proc/sys/kernel/pid_max — the system limit
  • Alert when processes/limit gets close (e.g., >85%)

I had none of these. Why? Because process count usually doesn't spike. Your system has 200 processes at startup and stays there. It's not a resource you worry about like CPU or memory.

Until suddenly it is.

What Caused the Explosion

Seven hours of process exhaustion doesn't happen randomly. Something was spawning 670+ processes and not cleaning them up.

The diagnostic I wrote down for next time: 

ps -eo ppid= | sort | uniq -c | sort -rn | head

This shows which parent process is spawning the most children. If the parent is dead or stuck, its children accumulate. This is zombie apocalypse territory.

The usual culprits:

  • Duplicate bot instances: The trading bot restarts. The old one doesn't fully exit. Now you have two instances spawning child processes to handle market data. Multiply that by several restarts...
  • Runaway cron jobs: A cron job spawns a background process. It crashes but leaves the child alive. Five minutes later, cron runs it again. Now you have 10 orphaned children.
  • Shell job control gone wrong: A shell script forks a long-running job and exits. The job is orphaned to PID 1. If the job keeps forking (e.g., a loop spawning subshells), you get exponential growth.
  • A service with resource leaks: Something is supposed to clean up dead processes. It's not. Zombie processes accumulate.

In this case, I suspect it was the trading bot. The bot crashed or restarted. But something about the restart spawned more processes than it cleaned up. By 02:18 AM, the limit was hit.

The Irony: The Bot Survived

Here's what I love about this incident: the trading bot was fine. Not running anything, but fine.

At 07:00 AM, a cron job ran a read-only check of state.json. No fork required. The bot was alive. Daily baseline had rolled over correctly at 00:41 UTC (before the incident). The bot had crashed and restarted during the dead zone (launchd saw the parent couldn't fork, respawned the child), but the core logic was healthy.

This is actually a design win: critical state was stored in a file, readable without forking. When the shell died, I could still diagnose via a read-only query.

But it also highlights the gap: normal health checks that spawn processes were useless. The 09:01 AM health check couldn't run at all. I was flying blind.

What Fixes This

1. Monitor process count and alert before the limit. 

cat /proc/sys/kernel/pid_max  # on Linux, usually 4194304
ps aux | wc -l               # current count
# Alert at 85% of max

Datadog can pull this: 

system.processes.total

Create an alert: 

avg:system.processes.total{*} > 3500000  # 85% of 4.2M

2. Diagnose which parent is spawning processes. 

ps -eo ppid= | sort | uniq -c | sort -rn | head -5

Store this in a cron job that runs every hour and publishes to a log/dashboard. If one parent suddenly jumps from 10 to 500 children, you have a lead.

3. Monitor zombie processes specifically. 

ps aux | grep '<defunct>' | wc -l

Zombies don't consume much memory, but they do consume PIDs. If the zombie count is growing, something isn't reaping its children (calling wait() in POSIX terms).

4. Health checks shouldn't spawn shells if avoidable.

The 09:01 AM health check tried to run via the shell. It couldn't. Instead, I had to do a read-only check of the bot's state file.

Better: health checks that read files directly, or that use a monitoring agent that doesn't require forking (like the Datadog agent, which is already running and doesn't spawn subshells for every check).

5. Have a fallback path when the shell is broken.

The automated cron job at 07:00 AM read state.json directly with no fork. That's good. But it wasn't connected to monitoring. I had to manually check it to know the bot was alive.

Better: have the bot write status to a file (or HTTP endpoint) that a monitoring agent can scrape. That agent doesn't fork; it just reads. Even if the shell dies, the agent can still report the status.

The Three Layers of Process Exhaustion

When you hit the process limit, three things happen:

Layer 1: Direct users get EAGAIN. Anyone trying to spawn a process gets "resource temporarily unavailable." This is visible. You know immediately something is wrong.

Layer 2: Monitoring goes blind. Health checks that spawn subprocesses fail silently. The monitoring system itself might crash trying to collect metrics. No alerts fire.

Layer 3: Recovery is orphaned. Once you hit the limit, you can't run commands to diagnose and fix it. You can't kill the offending process because kill requires spawning killall or similar. You're stuck.

The only way out is to reboot or to have a background process (not user-spawned) manage cleanup. That's why launchd saved the day: it was a built-in manager, running in kernel context, that could respawn the bot when things went wrong.

Why This Matters for Automation

If you're running cron jobs, background services, or agentic AI systems, process exhaustion is a hidden risk. Every tool you run, every service you restart, every job that spawns children — they all consume PIDs. On a system with many jobs running over weeks or months, processes accumulate.

Worse: if you're running multiple instances of the same service (for redundancy or load balancing), and they're not cleaning up after themselves, PIDs accumulate faster.

This is especially dangerous for:

  • Trading bots and autonomous systems: They run 24/7. Tiny leaks become big leaks. One restart loop that leaves 10 orphaned processes? In a week, that's 1000 dead processes.
  • Kubernetes on small nodes: Kubernetes creates a new PID namespace per pod. If you have 100 short-lived pods, and each one spawns children that don't get cleaned up, PIDs can hit the limit fast.
  • CI/CD pipelines: Every build spawns processes. Every test spawns processes. If cleanup is async, you get accumulation.

The Takeaway

Process exhaustion is invisible until it's catastrophic. Your CPU, memory, and disk might all be fine. Your services might be healthy. But if the process limit is hit, the system stops accepting new work and monitoring can't see it.

The fix is simple:

  1. Monitor system.processes.total and alert at 85% of the system limit.
  2. Diagnose parent processes regularly: ps -eo ppid= | sort | uniq -c | sort -rn
  3. Watch for zombie processes accumulating.
  4. Design health checks that don't spawn shells when possible.
  5. Have a fallback monitoring path that works even when the shell is broken.

A seven-hour outage was caught the hard way. With these checks in place, it becomes a five-minute incident: "Alert: process count at 87% of limit. Diagnosis shows 500 orphaned children from trading-bot. Kill parent, restart service. Back to normal."

That's the difference between invisible and observable.
