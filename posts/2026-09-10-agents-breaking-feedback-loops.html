When AI Agents Break Their Own Feedback Loop: Silent Failures in Autonomous Systems

2026-09-10
AI Agents Observability Autonomous Systems System Design DevOps

I built an agent system that reads a task queue, processes work, and writes results back to the same queue for the next iteration. On paper, it's elegant — a self-improving loop where each pass learns from the previous one. In practice, it silently failed for weeks, and every health check said everything was fine.

The problem wasn't the agent. It was the feedback loop itself.

The Setup

The agent runs on a schedule. Each run:

  1. Reads pending tasks from a queue
  2. Processes them with an LLM (Claude, in this case)
  3. Writes results back to the queue for downstream processing
  4. Marks tasks as complete

The next run reads the results as new inputs, refines them, and feeds the output forward. It's a classic agent loop — the kind of pattern you see in OpenClaw, ReAct, and tool-using systems everywhere.

Early runs worked flawlessly. The agent parsed tasks, called tools, got responses, and wrote clean results. I checked logs. All green. Passed validation. Shipped it.

The Silent Failure

Three weeks later, I realized the output had degraded into garbage. Tasks were being processed, but the results were incomplete, inconsistent, or nonsensical. The agent was working — it was reading input, generating output — but something fundamental had broken.

Here's what happened:

On the first run, the agent output was clean JSON. On the second run, that JSON became the input, and the agent processed it fine. On the third run, the output was slightly different — maybe a different field order, or a different format for dates. On the fourth run, that small difference cascaded. By the seventh or eighth iteration, the output had mutated into a format the downstream consumer didn't recognize.

The agent had not failed. It had never been given the same input twice. Each iteration saw slightly different data (my fault, I'd mutated the queue format mid-run). The agent adapted to each version, output something reasonable, and the next iteration adapted to that output. But the cumulative effect was drift.

All my monitoring showed:

  • "Agent ran: 1,247 tasks processed"
  • "Queue depth: 0"
  • "API calls: successful"
  • "Error rate: 0%"

Everything looked healthy. The system was actively working. It was just silently producing wrong answers.

Why Monitoring Misses This

Typical observability catches:

  • Crashes — process died
  • Errors — HTTP 500, exception thrown
  • Latency — API calls taking too long
  • Throughput — queue depth growing or shrinking unexpectedly

None of these apply to silent drift. The system:

  • Stays up and responsive
  • Never throws an exception
  • Runs at normal speed
  • Processes all work in the queue

It just produces garbage that looks reasonable until someone actually inspects the output.

With agents, this is worse because an LLM will often produce something plausible even with malformed input. It will reinterpret, interpolate, and hallucinate if needed. Your agent never stops and says "I don't understand this format" — it tries to make sense of it and keeps going.

The Invisible Contract

A feedback loop assumes a contract between the output of one iteration and the input of the next. That contract is typically invisible:

  • "Output is valid JSON"
  • "Field order doesn't matter"
  • "New fields are optional"
  • "Missing fields revert to defaults"
  • "All values pass the same validation as input"

If any assumption breaks, the loop degrades silently. The agent keeps working. The system keeps moving. But the fidelity drops with every iteration.

I had violated one assumption: I changed the queue format mid-run without versioning. One iteration's output was in format A, the next iteration's input expected format A, but by iteration three, I'd migrated to format B. The agent adapted to both, which meant neither was correctly specified anymore.

What Actually Works

1. Make the contract explicit and enforced.

Don't assume. Validate the output of every iteration against a schema. If it doesn't match, fail loudly: 

from jsonschema import validate

RESULT_SCHEMA = {
  "type": "object",
  "properties": {
    "id": {"type": "string"},
    "status": {"enum": ["pending", "done", "error"]},
    "output": {"type": "string"}
  },
  "required": ["id", "status", "output"],
  "additionalProperties": False
}

result = agent.process(task)

try:
  validate(instance=result, schema=RESULT_SCHEMA)
except jsonschema.ValidationError as e:
  log_error(f"Agent output does not match contract: {e}")
  mark_task_failed(task.id, "output_validation_failed")
  return

2. Version the contract, not the format.

If you change the schema, emit a version number. Each iteration should validate against a specific schema version: 

SCHEMAS = {
  1: {...},
  2: {...}
}

def validate_result(result, expected_version):
  schema = SCHEMAS.get(expected_version)
  if not schema:
    raise ValueError(f"Unknown schema version: {expected_version}")
  validate(instance=result, schema=schema)

3. Monitor the shape of the data, not just its throughput.

Track statistics on the output: average field count, value ranges, field presence. Alert when these drift: 

def analyze_output(result, iteration):
  stats = {
    "iteration": iteration,
    "field_count": len(result.keys()),
    "has_required_fields": all(k in result for k in ["id", "status", "output"]),
    "output_length": len(result.get("output", "")),
    "status_distribution": {...}
  }
  emit_metric("agent_output_shape", stats)

  # Alert if shape changes significantly
  if stats["output_length"] < 10:
    log_warning("Output suspiciously short")

4. Serialize in a canonical form.

If the agent outputs JSON, deserialize it, then re-serialize it in a canonical form (sorted keys, no extra whitespace). This prevents format drift: 

import json

result = agent.process(task)
parsed = json.loads(result)  # Fails if not valid JSON
canonical = json.dumps(parsed, sort_keys=True, separators=(',', ':'))

queue.enqueue(canonical)

5. Add a "generation number" to break cycles.

Track how many times this piece of data has been through the loop. If it exceeds a threshold, stop: 

def process_task(task):
  generation = task.get("generation", 0)

  if generation > 5:
    log_error(f"Task generation limit exceeded: {task.id}")
    mark_task_failed(task.id, "max_generations_reached")
    return

  result = agent.process(task)
  result["generation"] = generation + 1
  queue.enqueue(result)

6. Break the loop periodically and inspect.

Every N iterations, dump a sample of the data and compare it to the original input. If they've drifted, alert: 

SAMPLE_INTERVAL = 10

if iteration % SAMPLE_INTERVAL == 0:
  current = queue.peek(limit=5)
  original = archive.get_batch(iteration - SAMPLE_INTERVAL)

  drift = compare_shape(current, original)
  if drift > DRIFT_THRESHOLD:
    log_error(f"Data drift detected: {drift}")
    halt_queue()

The Real Problem

Feedback loops in agent systems are powerful. They let you iterate, refine, and improve results over time. But they're also fragile — because they hide failure in progress.

A crashed system is obvious. A system that's silently degrading is not.

The fix isn't to avoid feedback loops. It's to treat them like distributed systems: assume they will break in subtle ways, and add enough structure that when they do, you notice.

Summary

  • Agent feedback loops can silently degrade while all metrics report success
  • LLMs adapt to malformed input, preventing obvious errors
  • The contract between iterations must be explicit and enforced
  • Validate output shape, not just throughput
  • Version schemas and canonicalize formats
  • Monitor data drift, not just system health
  • Add generation limits to prevent infinite loops
