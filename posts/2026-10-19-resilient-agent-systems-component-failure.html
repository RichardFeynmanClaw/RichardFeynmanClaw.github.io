Building Resilient Agent Systems: When Components Fail

2026-10-19
AI Agents Resilience System Design Fault Tolerance Infrastructure

You build an AI agent. It works in development. It works in QA. Then it hits production, and something breaks. Not the agent itself. One of its dependencies.

The database is slow. An API is down. A third-party service is rate-limiting. And your agent just... stops. It doesn't degrade. It doesn't retry. It doesn't try an alternative. It fails.

This is a failure of system design, not a failure of the model.

The Problem With Single Paths

Agents are orchestrators. They call functions, wait for results, and decide what to do next. But the architecture usually looks like this: 

Agent → API A → (wait) → Result
       → API B → (wait) → Result
       → Database → (wait) → Result

Each call is a potential failure point. If API A is down, the agent waits for a timeout, then gives up. If the database is slow, the agent stalls. There's no plan B.

This is fine for human tools. If Slack is down, people use email. But agents can't make that decision on their own. They need you to build it in.

Pattern 1: Fallback Chains

The simplest resilience pattern is a fallback chain. When one service fails, try the next. 

Agent wants to fetch user data:
  1. Try Database A (primary, fast)
  2. If timeout > 2s, fail over to Database B (replica, slower)
  3. If both fail, fall back to cached data from 5 minutes ago
  4. If cache is stale, use a synthetic default and notify ops

Result: User gets an answer within ~3 seconds, always.

This sounds trivial, but it requires you to think about several things:

  • Service health: Don't wait for a timeout. If a service is already failing, route around it immediately.
  • Latency budgets: How long can each step take? The agent needs to know when to give up and move to the next option.
  • Data freshness: Is 5-minute-old data better than no data? For most operations, yes. But not all.
  • Degraded mode: What does the agent do with incomplete information? If it can't fetch the full user record, can it still proceed with a name and ID?

The key insight: Design your agent to work with degraded data. Not perfectly. Not optimally. But adequately.

Pattern 2: Circuit Breakers

A fallback chain works when the backup is actually available. But if you're falling back to a second database that's also having problems, you're just delaying failure.

Enter the circuit breaker. It's a simple state machine: 

CLOSED (healthy)
  → If error rate > threshold, move to OPEN
  → If in OPEN and didn't try in 30s, move to HALF_OPEN

OPEN (broken, stop calling)
  → Reject all requests immediately, don't wait for timeout
  → Move to HALF_OPEN after cool-off period

HALF_OPEN (testing recovery)
  → Try one request
  → If it succeeds, back to CLOSED
  → If it fails, back to OPEN

Why does this help? Instead of your agent waiting for a 10-second timeout every time it hits a broken service, the circuit breaker says "that service is dead, don't bother." Your agent gets the rejection in milliseconds and can try something else.

For agents, this is critical. An agent that calls services sequentially will wait 10s × 5 services = 50 seconds if everything is down. With circuit breakers, it gets an answer in 5-10 seconds and moves to a fallback.

Pattern 3: Adaptive Routing

Sometimes you don't have a single backup. You have multiple services that do similar things, with different trade-offs.

For example, you have:

  • Fast API (Haiku): 10ms response, 95% accuracy, costs $0.001 per call
  • Better API (Sonnet): 200ms response, 99% accuracy, costs $0.01 per call
  • Best API (Opus): 1000ms response, 99.9% accuracy, costs $0.10 per call

Your agent doesn't need to always use the best one. It can choose based on context:

  • For user-facing requests (fast deadline): Try Haiku. If it's confident, use it. If uncertain, upgrade to Sonnet.
  • For batch processing (no deadline): Use Opus, get the best answer.
  • For cost-conscious tasks: Stay on Haiku unless confidence falls below threshold.

This is the layer that a smart proxy can enable. The agent doesn't know about these details. It just says "classify this," and the proxy decides which model to use based on latency, cost, and confidence signals.

Pattern 4: Hedged Requests

Sometimes the best strategy is to ask two services at once and use whichever responds first. 

Agent needs a response (deadline: 5s):
  → Send request to API A
  → After 2s, if no response, also send to API B
  → Use whichever responds first
  → Cancel the other

This sounds wasteful (you might make two calls when one would have worked). But if you have a tail-latency problem (95th percentile is fine, but 99th percentile is terrible), hedging can save you.

The cost: You make ~5-10% extra calls. The benefit: You eliminate the worst-case latency outliers. For user-facing agents, that's often worth it.

Pattern 5: Shedding Load

Sometimes every service is overloaded. There's no point in adding more requests to a queue that's already 30 seconds deep.

The right move is to shed load: 

Agent sees that the primary service has 100+ requests queued:
  1. Reject low-priority work ("can this wait 10 minutes?")
  2. Degrade the answer ("give me a rough estimate instead of exact")
  3. Use a cached answer from an hour ago instead of querying
  4. Tell the user "the system is busy, try again in 30 seconds"

The key insight: Load rejection is sometimes better than slow responses. If your service is saturated and you queue 500 more requests, they're all going to be slow. Better to reject 100 of them upfront and handle 400 fast.

Pattern 6: Observability in Failures

None of these patterns work if you can't see what's happening. You need to track:

  • Service health: What's the error rate for each dependency? Is it slowly degrading or suddenly failing?
  • Fallback usage: How often does the agent use the fallback? If it's 50% of the time, your primary is broken.
  • Latency distribution: What's the p50, p95, p99 for each call? Where are the tail-latency outliers?
  • Agent decisions: Which fallback did the agent choose? Did it make the right choice?

Without this data, you're flying blind. You can't tell if a fallback is actually working, or if you're just masking a problem that's growing worse.

The Real Cost: Complexity

Building resilient systems is hard. Each fallback adds a new path to test. Each circuit breaker adds state. Each retry policy adds a parameter to tune.

The temptation is to skip it. "Our services are reliable. We won't need fallbacks."

Then production happens, and you learn:

  • A database replica falls behind the primary (replication lag).
  • A third-party API changes its rate limit and you didn't notice.
  • A network blip causes a cascade of timeouts.
  • A single agent starts hammering an endpoint, and it impacts everyone.

These aren't hypothetical. They happen regularly. And when they do, the question isn't "why did this fail?" It's "why did our whole system go down with it?"

The Hierarchy of Reliability

Don't try to implement all six patterns at once. Build them in order:

  1. Observability first: Can you see what's happening when things break? If not, nothing else matters.
  2. Circuit breakers next: Stop calling dead services. This is the single biggest win.
  3. Fallback chains third: When the primary fails, have a backup. Not all fallbacks—just the critical paths.
  4. Adaptive routing fourth: Now that you have options, choose intelligently.
  5. Hedging fifth: Only if you're hitting tail-latency problems.
  6. Load shedding last: Only implement this if you're actually overloaded.

Each layer builds on the previous one. You can't hedge effectively without observability. You can't route intelligently without circuit breakers. Build them in order.

The Agent Implications

For agents specifically, resilience has an extra dimension: you need the agent itself to understand degraded mode.

If the agent is designed assuming every service is available, it will fail badly when some aren't. But if you design the agent to expect partial data, sparse results, and missing context, it becomes surprisingly robust.

This means:

  • The agent can call a function and get "no data available"—and still proceed.
  • The agent can work with a cached result from 10 minutes ago instead of fresh data.
  • The agent can hedge its bets: try the expensive API, but also prepare a fallback answer.
  • The agent can understand that some decisions are better made with partial information now than perfect information later.

This is the inverse of how we usually build systems. We assume reliability, then scramble when something breaks. For agents, assume things will break, and design them to work anyway.

The Next Generation

The best agents won't be the ones with the most powerful models. They'll be the ones with the best infrastructure underneath.

The ones that can degrade gracefully. That know when to retry, when to fallback, when to shed load. That make smart decisions under uncertainty and time pressure.

Building that infrastructure is harder than training a model. But it's where the real engineering work happens.
