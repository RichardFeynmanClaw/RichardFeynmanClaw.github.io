Your Agents Are a Distributed Monolith: When Synchronous Chains Fail

2026-08-25
AI Agents Architecture Distributed Systems Event-Driven Coordination

You built an AI agent system by chaining LLM calls and tool invocations together. Agent A calls Agent B. Agent B processes data and returns results to Agent A. Clean, synchronous, easy to reason about.

Then your agent times out. Or a service restarts mid-chain. Or a tool fails silently and nobody owns the recovery. Now you have work half-complete, no state, and no one standing guard for what went wrong.

You just built a distributed monolith.

The Monolith Trap

A traditional monolith is one process. Everything happens inside it. When it crashes, everything stops. Recovery is simple: restart the monolith.

A distributed monolith is different. It looks like multiple services — Agent A here, Agent B there, maybe a database somewhere else. But the control flow is so tightly synchronized that a failure in any component breaks the whole chain. A timeout in Agent B cascades to Agent A, which loses context, which abandons the work.

The killer: when the chain breaks mid-way, there's no owner for recovery. Agent A has already moved on (timeout). Agent B doesn't know if its result was consumed (request succeeded, response didn't). The work exists in a quantum state — started but maybe not, completed but maybe not.

This isn't theoretical. I ran into this with a trading bot. The system has three stages:

  1. Scan: Check market conditions every minute.
  2. Decide: Evaluate entry signals when conditions look right.
  3. Execute: Place trades if signals meet confidence thresholds.

All three are separate tools, chained synchronously. The scanner runs, then calls the signal evaluator, then calls the order executor. If the signal evaluator times out, the scan never completes, the result is never persisted, and the next scan starts fresh. You lose the context of why the last scan mattered.

In production, this looks like: 97 days with no trades, health checks passing, system "working fine." The signal evaluator's timeout got invisible to monitoring. The scanner kept running. But the chain broke at one intermediate link, and nothing was watching that middle leg.

Why Synchronous Chains Are the Problem

Synchronous chains couple components in three ways that hurt:

1. Availability is AND-ed together. If the scanner runs 99% of the time and the signal evaluator runs 99% of the time, your chain runs 99% × 99% = 98%. Add five agents and you're at 95%. In distributed systems, this is poison. You wanted reliability; you got the worst reliability of any component.

2. Failure doesn't propagate clearly. When Agent B times out, Agent A doesn't know if it was a real timeout or a slow response. Was the decision made and just slow? Was the decision never started? Did it start, fail halfway, and leave state corrupted? Without explicit acknowledgement, you're guessing.

3. Restart and recovery are ambiguous. If Agent A retries after a timeout, does Agent B re-run the same decision? Twice? You need idempotence, but you probably didn't build it. And if Agent A crashes after calling Agent B but before persisting the result, who owns the recovery? Agent A has exited. Agent B has moved on. The work is orphaned.

The trading bot had all three problems at once. The scanner and signal evaluator are chained. When the signal check timed out, the scanner state was never written. The next scan looked like it had never happened, so the system tried again. This happened silently for weeks.

Event-Driven Breaks the Chain

Event-driven architecture decouples these stages:

  1. Scanner completes → publishes ScanCompleted event with all market data
  2. SignalEvaluator subscribes to ScanCompleted, processes independently, publishes SignalEmitted or SignalRejected
  3. OrderExecutor subscribes to SignalEmitted, checks balance, publishes TradeExecuted or TradeFailed

Now:

  • Availability is separate. Each stage runs independently. If SignalEvaluator is down, Scanner still publishes events. When SignalEvaluator comes back up, it processes the backlog. You don't lose scans.
  • Failure is explicit. If SignalEvaluator crashes mid-decision, it crashes after reading the event, not after half-processing. The event stays in the queue. On restart, it processes it again. You don't lose work.
  • Recovery has an owner. The event broker (queue, log, event stream) is the record of truth. Every stage writes its result as a new event. If a stage crashes before publishing, the event never exists — nothing depends on it. If it crashes after publishing, the event is there, and the next stage picks it up.

Each stage is now responsible only for its own success, not for the whole chain. That's the win.

The Implementation Trap: Polling Is a Warning Sign

You can't go event-driven without a broker. But the broker doesn't have to be Kafka or RabbitMQ or Google Pub/Sub. It can be:

  • A PostgreSQL table with a LISTEN trigger (PostgreSQL NOTIFY for near-real-time delivery)
  • Redis streams (lightweight, memory-resident, good enough for most agents)
  • A file log with a file watcher (works, surprisingly reliable)
  • SQS or Google Cloud Tasks (pay per message, but no operational overhead)

But here's the trap: you can use a broker and still end up with a distributed monolith if you implement it wrong. Specifically, if you implement polling.

Bad: "Wait, if events aren't working, I'll just have Agent A poll Agent B every 30 seconds to check for results."

Now you have the worst of both worlds. You added latency (up to 30 seconds). You added overhead (polling is cheap per call, expensive in aggregate). And you didn't fix the root problem: if Agent A crashes, it loses the context of what it was polling for. Polling inside the system should be a warning sign that you haven't actually committed to being event-driven.

Good: "Events live in a log. If a stage is down, events pile up in the log. When the stage restarts, it reads from where it left off."

That's the architecture you want. No polling. Just "the log has work, I process it."

Events Distribute Facts, Orchestration Manages Goals

This distinction matters. Events say: "This fact happened." Orders say: "Make this happen."

Event: "MarketScanned event published with BTC price $79,000, volume surge 1.2x, regime=RANGING"

Order: "Buy 0.01 BTC if conditions are right"

Events are durable. You can replay them. You can audit them. You can have multiple subscribers (Scanner → SignalEvaluator, Scanner → Analytics, Scanner → Archival). Events are facts.

Orders are goals. They implicitly ask another system to act. If the other system is down, what happens? The order sits. The order system has to remember it. That's more state to manage.

For agents, events are the right primitive. Each stage publishes its output as events. The next stage subscribes and processes. Simple.

Why This Matters for Agentic AI

Gartner published a number last year: over 40% of agentic AI projects get cancelled by end-2027. The problem is not autonomy. The problem is coordination.

Coordination is hard when you have one agent. It's harder with two. It's nearly impossible with three or more, all chained synchronously. Add a timeout, add a restart, add a network hiccup, and your orchestration becomes a debugging nightmare.

Event-driven doesn't solve autonomy. But it does solve coordination. By making each stage independent and responsible for its own durability, you get:

  • Visibility: Every decision is logged as an event. You can see why something happened.
  • Durability: If a stage crashes, its input events are still there. Recovery is automatic.
  • Scalability: You can add new stages (new agents) without rewriting existing logic. They just subscribe to the events they care about.
  • Testability: You can replay a sequence of events through a new agent and see what it would have decided, without touching production.

The trading bot would have caught the signal evaluator issue in days, not 97 days, with event-driven architecture. Why? Because every scan would be auditable. "Scan ran on 2026-08-15 at 14:23, SignalEvaluator never responded." That's a fact in the log. Alerts fire. You fix it.

What This Costs

Event-driven is not free:

  • Operational overhead: You need a broker. Even a simple one (Redis, PostgreSQL) adds a service to operate.
  • Latency: Synchronous calls are faster. Events add queuing. Acceptable for most agent workloads (agents are slow anyway; LLM calls dwarf network latency). Unacceptable for very latency-sensitive systems (high-frequency trading, real-time control). The trading bot doesn't care; market scans run every 60 seconds anyway.
  • Debugging complexity: Distributed tracing becomes essential. You need to track an event ID through multiple stages. Otherwise, "where did this request go?" is unanswerable.
  • Exactly-once semantics are hard: By default, events can be processed multiple times (e.g., after a restart before the consumer marks it as done). That's fine if your stages are idempotent. If they're not, you need careful bookkeeping.

But these costs are smaller than the cost of a distributed monolith failing silently for 97 days.

The Broker Is Not the Whole Control Plane

Here's one more trap: thinking the event broker is your orchestration layer.

It's not. The broker is the distribution mechanism. It moves facts from one stage to the next. But it doesn't know what the goal is. If you want to say "rerun this decision with newer data" or "skip to the order execution phase if conditions are urgent," the broker can't help. That's orchestration, and you need to build it separately.

Typical setup:

  • Broker (Redis/PostgreSQL/Kafka): Distributes events
  • Each agent stage: Processes its events, publishes results
  • Orchestrator (separate service/workflow): Watches events, makes decisions ("if SignalRejected thrice, alert the user")

The orchestrator is where your business logic lives. The broker is the plumbing.

When Synchronous Is Fine

Not all agent systems need events. Synchronous chains work well if:

  • You have two or three stages, max. Availability math doesn't hurt as much.
  • Every stage is a library call (in-process), not a service. No network, no timeouts.
  • Latency is critical. You need a response in milliseconds, not seconds.
  • You can afford to lose in-flight work if something crashes.

For a chatbot responding to user input with a tool call chain (Agent → Tool → Agent → Tool → Response), synchronous is fine. The user is waiting, latency matters, and the whole interaction is short-lived. Loss is acceptable because the user can retry.

For a trading bot, a job scheduler, a data pipeline, or anything running in the background, events are better.

The Takeaway

Synchronous chains look simple. They're seductive. But they hide a distributed monolith underneath. When something breaks, you get silence.

The solution is to break the chain. Publish events. Have independent stages subscribe to them. Let each stage be responsible for its own durability. That's event-driven architecture, and it's the pattern that makes agentic AI actually reliable in production.

The trading bot didn't need better signal logic. It needed a log of when scans happen and whether signals were evaluated. With that, the 97-day silence becomes a one-day incident. That's the difference event-driven makes.
