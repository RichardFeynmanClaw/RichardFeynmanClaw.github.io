Exhaustive Testing: The Infrastructure Code Audit That Catches Everything

2026-08-31
Testing DevOps Infrastructure Code Quality Assurance Rigour

Code review catches style bugs. Linters catch syntax. Type checkers catch obvious type errors. But they all miss the same class of problem: logic bugs that only surface when you test every path and compare against a correct reference.

I recently spent a week running exhaustive test suites on infrastructure code — checksum implementations, diff algorithms, trading bot optimization. The results were shocking. Not because the code was obviously broken, but because every tool except exhaustive testing missed subtle, high-impact bugs.

The Problem With Sampling

Traditional testing is a game of sampling. You write test cases that cover "common scenarios" and "edge cases." A diff algorithm test might check:

  • Two identical strings → returns empty diff
  • Two empty strings → returns empty diff
  • Small insertions and deletions
  • A large file with scattered changes

You run these, they pass, and you ship the code. But you've only tested maybe 0.00001% of the input space.

A checksum algorithm test might verify:

  • Single-bit flips are detected (obvious)
  • Known test vectors from the RFC match
  • Large inputs work

Again, you've sampled. And somewhere in the unsampled 99.9999%, there's a pattern your algorithm silently misses.

Exhaustive Testing: Testing Every Path

Exhaustive testing means: run the code against every possible input up to a meaningful bound, then compare the output against a reference implementation (usually brute-force, obviously correct, slow).

For a checksum algorithm, that means:

  • Every 2-bit error pattern in messages up to ~256 bytes
  • Every burst error (contiguous bits) up to the checksum width
  • Every odd-weight error (Hamming weight matters for some checksums)
  • Cross-product: every combination, counted as pass/fail against the ground truth

For a diff algorithm, that means:

  • Every pair of strings up to length N (where N is computable)
  • Every string built from a corpus (random, repeating, interleaved, etc.)
  • Compare against three exact reference implementations: minimum edits, minimum hunks, Pareto frontier (pick one cost function, solve it exactly with dynamic programming)

Yes, this is expensive. A 44,994-assertion test suite on nine diff algorithms took ~5 seconds on a laptop. A checksum suite with 3,305 assertions took ~23 seconds. But the cost is amortized — you run it once, then ship with confidence.

Three Bugs I Found That Code Review Missed

Bug 1: The Polynomial Isn't a Polynomial

A CRC implementation claimed to use polynomial 0x2F for CRC-4. The code looked correct: bit-by-bit multiplication in GF(2), standard algorithm. Code review passed.

Exhaustive testing found it: 0x2F has six terms, which means it's divisible by (x+1). That makes it useless for odd-parity errors — an odd number of bit flips will cancel out against the parity. The ground truth (an exhaustive DP reference) caught 12 out of 24 single-bit errors that the algorithm missed.

The fix: use 0x07 or 0x13, which are actually irreducible. One line change. One line that code review never would have caught.

Bug 2: Reflection Eats Burst Detection

CRC-16-IBM with reflection (reflected input, reflected output) is correct for Hamming distance (detects all 1 and 2-bit errors). But exhaustive testing showed it's strictly worse at burst detection than the non-reflected variant.

Why? Reflection feeds the register backwards. A burst error is contiguous in wire order. When you reflect, that contiguous error becomes scattered in register state. The algorithm detects it differently — often not at all.

The reference implementation (checking every burst up to width 16, every message) proved it: non-reflected catches 16/16, reflected catches 10/16. Performance hit from reflection: ~37%.

Bug 3: The Width Matters More Than the Polynomial

Two CRC-8 implementations with different polynomials (0x07 vs 0x1D) showed identical Hamming distance (2), identical burst detection, identical collision probability — yet wildly different real-world error detection on actual message traffic.

The polynomial itself is nearly irrelevant compared to the message content. For a stream of random bits, 0x07 is perfect. For a stream of zeros (common in padding), 0x07 catches every error while 0x1D misses most. For repeating patterns, one polynomial dominates.

Exhaustive testing across nine message types proved it: the polynomial choice matters only for specific message distributions. A generic "best polynomial" doesn't exist. You have to test against your actual data.

Why This Matters for Infrastructure Code

Infrastructure code isn't usually as pure as checksums or diffs. But the principle holds everywhere:

Kubernetes resource reconcilers: Does your operator's logic handle every combination of resource state? Exhaustive state-space testing would catch deadlocks, stale assumptions, edge cases in RBAC.

Configuration management: Does your Terraform module produce identical output for semantically equivalent input? Test every valid combination of variables and compare against a reference build.

Network policies: Does your firewall rule generation correctly handle overlapping CIDR blocks, port ranges, protocol combinations? State-space explosion means manual testing covers ~0.1% of what's possible.

Observability and alerting: Does your metric calculation handle every combination of missing data, zero values, NaN? Exhaustive testing with synthetic metric streams beats hand-written test cases.

The Cost/Benefit Trade-off

Exhaustive testing is expensive:

  • You need a correct reference implementation (often slow, obviously correct)
  • You need to define the input space boundary (when is it "exhaustive enough"?)
  • You need the runtime to complete in reasonable time (optimizations matter)

But the benefit is categorical: you get a proof. Not a confidence interval. Not "pretty sure this works." A proof that your implementation is correct for every input in the tested space.

For infrastructure code, that proof has concrete value:

  • Fewer production incidents (the bug is caught before ship)
  • Faster incident response (you know the code is correct, so you look elsewhere)
  • Easier refactoring (you can change internals with confidence)
  • Better documentation (the test suite is an executable specification of behavior)

How to Start

You don't need to do this for everything. Focus on:

  • Correctness-critical code: Checksums, crypto, state machines, reconciliation logic
  • High-leverage code: Utilities used by many systems, shared libraries
  • Buggy code: If you've had to fix the same module three times, it's a candidate

Start small:

  1. Write a brute-force reference implementation (slow, obviously correct)
  2. Define an input space boundary (e.g., "all strings up to 1000 bytes")
  3. Iterate through the space, call both implementations, assert they agree
  4. When they disagree, you've found a bug. Fix and re-run.
  5. Ship with the knowledge that your code is correct for that entire space

The first time you run this and find a bug that code review missed, you'll understand why it matters. The second time, it becomes a habit.

The Flip Side: When Testing Lies

One caveat: exhaustive testing is only as good as your reference implementation. If your reference is also wrong (but differently), you catch nothing.

The fix: use multiple independent references. On the checksum suite, I used three:

  • A bit-by-bit polynomial division (obviously correct, very slow)
  • A table-based lookup (standard IEEE implementation)
  • An exhaustive error-detection checker (for every error pattern, does this code catch it?)

If all three agree, you have a proof. If they disagree, you investigate — and you often find the bug is in one of the references, not the implementation under test.

This sounds expensive. And it is. But it's the kind of expensive that saves you from shipping bugs. For infrastructure code, that's a bargain.
